[ Gemstone Sorting Robot - System Overview & Handover Guide ]

เอกสารฉบับนี้จัดทำขึ้นเพื่อส่งมอบงานให้กับนักพัฒนาท่านอื่น (Handover) เพื่อให้สามารถอ่าน ทำความเข้าใจ และสานต่องานได้ทันที โค้ดทั้งหมดได้ผ่านการ Review มาแล้ว 4 รอบ (V4 Final Polish) และอยู่ในระดับ Competition Ready (เสถียร 100% ในระดับลอจิก) 

โค้ดทั้งหมดถูกรวบรวมไว้ที่โฟลเดอร์เดียวกันนี้พร้อมใช้งาน

=======================================================
1. ภาพรวมสถาปัตยกรรมระบบ (System Architecture)
=======================================================
ระบบแบ่งออกเป็น 2 ส่วนหลัก ทำงานร่วมกันแบบ Client-Server ผ่านเครือข่าย Wi-Fi:

1. Host (คอมพิวเตอร์ / Python):
   - ทำหน้าที่เป็น "สมอง" และ "ดวงตา" รับภาพจากกล้อง Webcam (มุมมอง Top-down) 
   - ใช้ OpenCV ตรวจจับหุ่นยนต์ (ArUco Marker ID: 0) และหิน (HSV Color Masking)
   - รัน FSM (Finite State Machine) เพื่อตัดสินใจ และ Path Planner (PD Controller) เพื่อคำนวณความเร็วมอเตอร์
   - ส่งคำสั่งความเร็วมอเตอร์ (vL, vR) และองศาประตู (doorL, doorR) ไปยัง ESP32 ในรูปแบบ JSON ผ่าน WebSocket

2. Client (ESP32 / C++):
   - ทำหน้าที่เป็น "กล้ามเนื้อ" ปล่อยสัญญาณ Wi-Fi Hotspot (SSID: GEMSTONE_ROBOT) และเปิด WebSocket Server ที่ Port 81
   - รอรับ JSON payload นำมาแกะและสั่งงาน Motor Driver ผ่าน Native PWM (ledc) และสั่ง Servo
   - มีระบบ Safety: ถ้าขาดการติดต่อจากคอมพิวเตอร์เกิน 0.5 วินาที จะตัดการทำงานมอเตอร์ทันทีป้องกันรถวิ่งชน

=======================================================
2. สถานะปัจจุบัน (Current Status)
=======================================================

[ สิ่งที่ทำเสร็จสมบูรณ์แล้ว (100% Ready) ]
- Networking: WebSocket สื่อสารสองทางเสถียร, มี Safety Timeout (ฝั่ง ESP32), มี Auto-reconnect (ฝั่ง Python)
- Motor & Servo Control: โค้ด ESP32 ใช้ Native PWM (ledc) ซึ่งนิ่งและเสถียรมากสำหรับชิป ESP32
- Door Control: ผสานระบบ DoorControl2 เข้ากับเฟิร์มแวร์ ESP32 เรียบร้อย (คุมประตูเก็บหินแบบใช้สูตรคำนวณองศาอัตโนมัติ และรับคำสั่ง "collect", "release", "close" จาก Python แทนองศาดิบ พร้อมระบบป้องกับหินตกหาก Wi-Fi หลุด)
- Vision Tracking: จับตำแหน่งรถ (พิกัดและมุม Heading) ผ่าน ArUco, จับหิน 6 สีผ่าน HSV, แก้ปัญหาภาพเบี้ยวด้วยระบบพิกัดมิลลิเมตร (MM-space)
- Path Planning: ขับรถเข้าหาเป้าหมายอย่างสมูทด้วย PD Controller, ระบบสุ่ม Waypoint อ้อมกองหินตรงกลาง (Danger Zone)
- Strategy: อัลกอริทึมเลือกหินจากวงนอกสุด (Outer Ring) ก่อน เพื่อลดความเสี่ยงชนกองหิน
- Core FSM: State Machine แบบ Non-blocking (ใช้ time.time() แทน time.sleep()) ทำให้ระบบไม่ค้าง มี Timeout ดักจับทุก State ที่มีโอกาสตายค้าง (เช่น ตามหาหินไม่เจอ หรือเดินหน้าชนขอบ)

[ สิ่งที่ยังต้องทำต่อ (Pending Tasks / Hardware Tuning) ]
ส่วนนี้คือสิ่งที่คุณต้องรับช่วงต่อ (เน้นไปที่ Hardware และ Gameplay Mechanics):
1. ระบบเก็บและวางหิน (Ingest & Unload Mechanics):
   - 🔴 (อัปเดตแล้ว): ระบบควบคุมประตู (DoorControl) ทำงานสมบูรณ์แล้วผ่านคำสั่ง door_cmd เหลือเพียงแค่นำโค้ดสั่งมอเตอร์ "ลูกกลิ้ง" มาใส่เพิ่มเติมหากมีการติดตั้งฮาร์ดแวร์ลูกกลิ้งในอนาคต
2. Hardware Calibration (หน้างานจริง):
   - จูนมุมกล้องและตั้งค่า Homography Matrix ใน vision_tracker.py ให้ตรงกับสเกลสนามจริง (2100x1200 mm)
   - รันไฟล์ calibrate_hsv.py ภายใต้แสงไฟสนามจริง เพื่ออัปเดตค่าสีหินใน hsv_config.json
   - ตรวจสอบว่าด้านหน้าของหุ่นยนต์ (Front) ตรงกับขอบ (Edge) ไหนของ ArUco Marker
3. Gesture Controller (Phase ต่อไป):
   - ยังไม่มีการเขียนระบบ MediaPipe ควบคุมด้วยมือ (หากจำเป็นต้องใช้ตามกติกา ต้องเขียนโมดูลนี้มาต่อคั่นก่อนเข้า FSM)

=======================================================
3. เจาะลึกโค้ดทีละไฟล์ (Deep Dive)
=======================================================

* robot_logic.py (สมองสั่งการหลัก)
- หน้าที่: รัน FSM (Finite State Machine) จัดการลำดับการทำงานทั้งหมดของหุ่นยนต์
- การทำงานหลัก:
  - update(): ฟังก์ชันหลักที่ถูกเรียกทุกเฟรม มันจะไปดึงข้อมูลตำแหน่งจากกล้อง, เช็คว่าหมดเวลา 5 นาทีหรือยัง และสลับ State การทำงานตาม FSM
  - FSM Flow: SCAN_OUTER_RING (เลือกหิน) -> ALIGN_APPROACH (หันหน้ารถเข้าหาหิน) -> [โซนเก็บหิน] -> CHECK_CAPACITY (เช็คว่าเต็มยัง) -> NAV_WAYPOINTS (วิ่งกลับฐาน) -> [โซนคายหิน] -> วนลูปกลับไปสแกนใหม่
- จุดสำคัญสำหรับคนทำต่อ:
  - ให้ค้นหาคำว่า "ZONE: ระบบเก็บหิน" ในไฟล์นี้ สเตท DRIVE_INGEST, LOCK_DOORS, BACKOUT_CLEAR, และ UNLOAD_REVERSE คือจุดที่คุณต้องเอาลอจิกสั่งมอเตอร์ลูกกลิ้งมาใส่ (ปัจจุบันระบบประตู DoorControl ทำงานเสร็จสมบูรณ์แล้วผ่านคำสั่ง door_cmd)
  - ทุก State ที่มีการหน่วงเวลาจะใช้ time.time() - self._state_timer ห้ามใช้ time.sleep() เด็ดขาดเพราะจะทำให้กล้องและเครือข่ายค้าง

* esp32_firmware.ino (เฟิร์มแวร์รถ)
- หน้าที่: รับคำสั่ง JSON ผ่าน WebSocket ไปขับมอเตอร์และสั่งงานประตู (DoorControl2)
- การทำงานหลัก:
  - ใช้ไลบรารี WebSocketsServer และ ArduinoJson รอรับข้อมูลรูปแบบ {"vL": 150, "vR": 150, "door_cmd": "collect"}
  - ใช้ฟังก์ชัน ledcWrite() ขับมอเตอร์ (ESP32 ไม่มี analogWrite ธรรมดา)
  - ใช้ไลบรารี DoorControl บริหารจัดการประตู (คำนวณมุมง้างจากสัดส่วนหุ่นยนต์ และดูแลระบบความปลอดภัย)
- จุดสำคัญสำหรับคนทำต่อ:
  - ต้องเปลี่ยน password123 ให้เป็นรหัสผ่านที่ปลอดภัยก่อนแข่งจริง
  - หากต่อ Servo/Motor ผิดพิน ให้แก้ที่ #define ด้านบนสุดของไฟล์
  - ระบบมี Timeout: บรรทัดล่างสุดใน loop() ถ้า Wi-Fi หลุดเกิน 500ms รถจะหยุดเองทันที

* vision_tracker.py (ดวงตาวิเคราะห์ภาพ)
- หน้าที่: แปลงภาพจากกล้องเป็นข้อมูลพิกัด (X, Y) แบบมิลลิเมตร
- การทำงานหลัก:
  - detector.detectMarkers: หา ArUco (หุ่นยนต์) คืนค่ามาเป็นพิกัดกึ่งกลาง และแปลงพิกัดมุมรถเพื่อหาว่ารถกำลังหันหน้าไปทิศไหน (Heading -atan2)
  - cv2.inRange: ทำ Color Masking หาหินสีต่างๆ ด้วยค่า HSV จากไฟล์ Config
- จุดสำคัญสำหรับคนทำต่อ:
  - ระบบพิกัด (Coordinates) ถูกดัดแปลงเป็น มิลลิเมตร (mm) หมดแล้ว (ซ้ายบน = 0,0 | ขวาล่าง = 2100, 1200) เพื่อแก้ปัญหาภาพกล้อง (4:3) กับสนามจริง (7:4) สัดส่วนไม่เท่ากัน
  - สีแดงใช้ Dual-Mask (bitwise_or) ดักจับทั้งช่วง Hue 0-10 และ 170-179 เพื่อแก้ปัญหาขอบสีแดง

* path_planner.py (ระบบขับเคลื่อนและเลี้ยว)
- หน้าที่: คำนวณความเร็วมอเตอร์ซ้าย/ขวาเพื่อให้รถวิ่งเข้าหาเป้าหมาย และหาเส้นทางหลบสิ่งกีดขวาง
- การทำงานหลัก:
  - calculate_steering(): ใช้คณิตศาสตร์หาผลต่างมุม (Error) ระหว่างทิศที่รถหันอยู่ กับทิศที่เป้าหมายอยู่ จากนั้นใช้ PD Controller (Proportional-Derivative) เติมความเร็วให้ล้อใดล้อหนึ่งเพื่อดึงรถให้หันตรงเป้าหมาย
  - generate_perimeter_waypoints(): ถ้ารถต้องวิ่งกลับฐานแต่มีกองหินตรงกลาง (Danger Zone) ขวางอยู่ ฟังก์ชันนี้จะสร้าง "จุดพัก" (Waypoint) ให้รถวิ่งอ้อมเป็นรูปตัว L ทันที
- จุดสำคัญสำหรับคนทำต่อ:
  - self.Kp_heading = 2.0 และ self.Kd_heading = 0.5 อาจจะต้องจูนใหม่เมื่อวางหุ่นลงสนามจริง (ถ้าเลี้ยวส่ายไปมา ให้ลด Kp ถ้าเลี้ยวช้าไป ให้เพิ่ม Kp)
  - DANGER_ZONE (ตำแหน่งกองหินกลางสนาม) ถูก Hardcode ขอบเขตพิกัดไว้ที่ L16-19 สามารถปรับแก้ได้ตามของจริง

* strategy_engine.py (สมองกลยุทธ์)
- หน้าที่: ตัดสินใจว่าจะเก็บหินสีอะไร และก้อนไหนก่อน
- การทำงานหลัก:
  - analyze_outer_ring_color(): คัดหิน 15 ก้อนที่ไกลจากศูนย์กลางที่สุด (วงนอก) มาหาว่าสีไหนมีเยอะสุด จะได้เป้าหมายสีนั้น (ช่วยลดการทำลายกองหินกลางสนาม)
  - find_best_stone(): หินก้อนที่จะไปเก็บ ต้องเป็นก้อนที่ 1) อยู่ขอบนอก และ 2) อยู่ใกล้รถ (ถ่วงน้ำหนักคะแนนผสมกัน)
- จุดสำคัญสำหรับคนทำต่อ:
  - ระบบเสถียรดีแล้ว แทบไม่ต้องปรับแก้ เว้นแต่ต้องการเปลี่ยน Strategy การเล่น

* calibrate_hsv.py (เครื่องมือจูนสี)
- หน้าที่: สคริปต์แยก (UI มี Trackbar) สำหรับจูนค่าสีกล้อง
- การทำงานหลัก: รันสคริปต์นี้ ปรับแถบเลื่อนจนกว่าหินสีที่ต้องการจะกลายเป็นสีขาว (Mask) สว่างชัดเจน จากนั้นกดปุ่ม 's' เพื่อบันทึกลงไฟล์ hsv_config.json
- จุดสำคัญสำหรับคนทำต่อ: ต้องนำไปรันที่หน้างานจริงเสมอ เนื่องจากแสงไฟฮอลล์แข่งกับห้องซ้อมไม่เหมือนกัน
